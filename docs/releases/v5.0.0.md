# RedlineDB v5.0.0

Released 2026-09-29; the `v5.0.0` tag names the source commit.

> **Experimental release.** RedlineDB is not a replacement for SQLite. It uses
> its own file format, its C ABI is an experimental subset of `sqlite3_*`, its
> PostgreSQL support is a SQL-shell corpus with no wire protocol, and its
> durability claim covers a process crash in `Strict` mode, not power loss.
> On the per-process CLI benchmark it is slower than SQLite. Read
> [Known limitations](#known-limitations) before you upgrade.

v5.0.0 is the first release from the canonical repository,
[neverhuman/redline](https://github.com/neverhuman/redline). It follows v4.1.0
and changes the on-disk index format, the C ABI and the install layout, so it
is a major version.

## Highlights

- **Crash recovery and WAL.** A checkpoint writes every dirty page as one
  complete cut; it used to skip pages another writer changed after it chose
  its LSN, and lose the committed rows they held. Recovery checks the WAL
  against the checkpoint before it changes any file and fails the open
  instead of silently losing commits; it never hands out a transaction id the
  log already used (in v4.1.0, after a rollback and a clean reopen, the next
  commit could make the rolled-back rows reappear at the following reopen);
  it never restarts the WAL below the checkpoint; and it copies a torn log
  tail to `wal/salvage/` before it cuts it. The database root, the `wal`
  directory and each new segment name are fsynced before a commit that
  depends on them is acknowledged. A commit whose log write fails after its
  record was queued reports an uncertain outcome instead of a rollback, and
  `COMMIT` returns only once a new transaction sees it. An open takes
  `owner.lock` before it recovers anything.
- **A durability contract.**
  [`docs/manual/durability.md`](https://github.com/neverhuman/redline/blob/v5.0.0/docs/manual/durability.md)
  states what each durability mode survives. Its one claim, `Strict` survives
  a process kill, is backed by a receipt taken on the shipped shell, and the
  release is published only with that receipt. `PRAGMA redline_durability`
  reads back the mode in force, and `PRAGMA redline_recovery_report` says
  what the last recovery did.
- **SQL correctness.** SQLite's comparison affinity in `WHERE`, `IN`,
  `BETWEEN`, joins and index probes; integer overflow; exact INTEGER/REAL
  comparison; declared column collations in comparisons, sorting, grouping,
  indexes and `UNIQUE`; set operations and `GROUP BY` on SQLite value
  equality; positional `ORDER BY`; partial indexes kept in step on `UPDATE`,
  and `PRAGMA integrity_check` comparing every index with its table; CTE
  scoping, and statements that re-read views, CTEs and derived tables when
  they run; recursive CTEs under `LIMIT`; trigger chains; `SAVEPOINT` and
  `ROLLBACK TO`; and a working `REINDEX`.
- **Stricter, published SQLite comparison.** Every case is held to its declared
  exit code, error text and byte-exact output against the pinned sqlite3 3.53.1
  shell. Each failing case is published with its reason, skips are allowed only
  where the scope policy lists them, and the badge names exactly what was
  measured.
- **PostgreSQL shell evidence by outcome.** Row matches, expected rejections,
  declared-unsupported cases and mismatches are counted separately, and the
  block is published only from a clean source tree at the expected commit.
  Session functions that answered with stand-ins now do the work (advisory
  locks, `txid_current()`, `pg_wal_lsn_diff()`) or refuse
  (`pg_current_wal_lsn()`, `pg_export_snapshot()`, `pg_notify()`, `NOTIFY`).
- **Reproducible version history.** Past releases are rebuilt from their
  commits and re-run on today's corpus; the README table is rendered from that
  bundle, and the note under it says how it was measured.
- **C ABI v5.** Upstream `sqlite3_prepare_v3` argument order, `SQLITE_NULL`
  = 5, column text and types that follow each value's storage class, an
  ephemeral `:memory:`, registrations tied to their connection, flags and
  callbacks RedlineDB cannot honour refused instead of ignored, and a versioned
  library (`libredlinedb.so.5`, `libredlinedb.5.dylib`).
- **Install and release.** Checksummed archives with build provenance bound to
  this repository and tag, attestations, and an installer that keeps each
  version in its own directory and switches with one rename, so a failed
  install leaves the previous version working. `LICENSE` is the full
  Apache-2.0 text, with a `NOTICE`, and archives carry the licence texts of
  the code they ship. `SECURITY.md` names a private reporting route.

## Breaking changes and migration

### Back up before upgrading

v5.0.0 rewrites index data the first time it opens a database written by v4,
and v4 refuses the database afterwards when it has an index. Take a physical
backup **with your current v4 binary** first (every v4 release has
`backup … --physical`):

```bash
redlinedb backup /path/to/db /path/to/db-v4-backup --physical
```

Databases written before v4 have not been tested with v5.0.0.

### Database files

- **Index-format epoch 3.** The first open of a database written by v4
  rebuilds every index from the table rows, expression and partial indexes
  included, in one transaction, before the database is handed out. The
  rebuild applies the v5 rules: INTEGER and REAL keys share one numeric key
  space (`1` and `1.0` are one key), a column's declared `NOCASE` or `RTRIM`
  collation applies to index keys and `UNIQUE` constraints that name no
  collation of their own, and expression keys and partial-index predicates
  are evaluated with v5's SQL semantics. This also repairs partial indexes
  that a v4 `UPDATE` left out of step with their rows.
- If a `UNIQUE` index would then hold two rows with one key (for example `1`
  and `1.0`, `'x'` and `'X'` in a `NOCASE` column, or two rows a v4 partial
  `UNIQUE` index let in), the open fails with `UNIQUE constraint failed`,
  names the index, and changes nothing. Remove the duplicates with a v4
  binary, then open again with v5.
- After the rebuild, v4 refuses a database that has any index (v4.1.0 prints
  `unsupported format version: 3`). The control file is now format 2 and a
  catalog that stores collations is format 8, which v4 does not know either;
  opening a v5 database with v4 is not supported. Keep the backup if you may
  need to downgrade.
- A restore to a target LSN or CSN now records where it cut, so later opens
  stay at the target. A binary older than v5.0.0 ignores that record and
  replays past the target.
- The file format is still RedlineDB's own. SQLite cannot open it, and
  RedlineDB cannot open SQLite files.

### Opening a database

- An open takes `owner.lock` before it reads or recovers anything, and holds
  it until the last `Database`, `Connection` and prepared `OwnedStatement` of
  that database are gone. A rejected open leaves the files untouched.
- A read-only open (`OpenOptions.read_only`) takes the same exclusive lock,
  so it gets `Busy` while another process has the database open. It used to
  skip the lock and still run recovery.
- A `COMMIT` whose log write or fsync failed after its record was queued
  returns `CommitMaybeCommitted` ("commit outcome uncertain",
  `ErrorCode::IoErr`, `RLDB_IOERR`); the transaction may be there after a
  reopen. After any log failure, writes fail until the database is reopened.

### SQL results and errors

These apply to the default SQLite dialect unless noted.

- `SUM()` over integers that overflows raises `integer overflow`, as in
  SQLite, on every execution path. Integer `+`, `-`, `*` and unary minus that
  overflow produce a REAL; `abs()` of the minimum integer is an error. In the
  PostgreSQL dialect an integer overflow is `bigint out of range`.
- Comparisons use SQLite's comparison affinity: `WHERE x = '5'` on an
  INTEGER column finds 5, and `WHERE y = 5` on a TEXT column finds `'5'`.
  INTEGER and REAL compare exactly.
- Text operands follow SQLite: `'1abc' + 1` is 2, `'7' / '2'` is 3,
  `'[1]' || '[2]'` is `[1][2]`, and `'2025-01-02' - '2025-01-01'` is 0.
  Standard `CAST(x AS DATE)` (and `TIMESTAMP`, `BOOLEAN`, `UUID`, `JSON`,
  `MONEY`) is a NUMERIC cast, so `CAST('2025-01-02' AS DATE)` is 2025.
  `::` casts and the PostgreSQL dialect keep the PostgreSQL readings.
- Text and BLOB truth values use SQLite's numeric prefix (`'1abc'` is true,
  `'abc'` is false).
- A column's declared `NOCASE` or `RTRIM` collation applies wherever SQLite
  applies it. A `UNIQUE` constraint on such a column now rejects `'x'` after
  `'X'`. An index key collation other than `BINARY`, `NOCASE` or `RTRIM` is
  refused.
- `UNION`, `INTERSECT`, `EXCEPT`, `GROUP BY` and `DISTINCT` aggregates treat
  `1` and `1.0` as one value.
- `ORDER BY 0`, a negative position or one past the last column fails with
  `1st ORDER BY term out of range`; a position now always sorts by that
  result column.
- `CREATE VIEW` with a parameter in its body is refused, as in SQLite.
  Statements that read a view, a CTE or a derived table bind again when they
  run, so a prepared statement reads current rows and bound parameters.
- `ROLLBACK TO` refuses, before changing anything, when a statement before
  the savepoint cannot be replayed exactly (it read the clock or a random
  value, called a user-defined or PostgreSQL function, fired a trigger, used
  `RETURNING` or changed the schema, among others); the transaction must then
  be rolled back. `SAVEPOINT`, `RELEASE` and `ROLLBACK TO` act when stepped,
  not when prepared.
- With `recursive_triggers` off (the default), a trigger fired by another
  trigger's body now runs; only a trigger that is already running is
  skipped, as in SQLite. Trigger programs nest at most 8 deep.
- `REINDEX` rebuilds indexes (it did nothing). It commits only once its
  transaction is the only one open, waiting up to the busy timeout, and
  otherwise fails with `lock timeout` and changes nothing.
- The SQL dialect is a per-database option (`OpenOptions::with_dialect`,
  `DbOptions::dialect`). `REDLINEDB_RESULT_DIALECT` is read once, when a
  database opens without that option; the shell reads it once at startup.
- In the PostgreSQL dialect, `pg_current_wal_lsn()`, `pg_export_snapshot()`,
  `pg_notify()` and `NOTIFY` fail with `unsupported capability:` instead of
  answering with a stand-in, and the PostgreSQL block counts those cases as
  declared unsupported. Advisory locks, `txid_current()` and
  `pg_wal_lsn_diff()` now do the work. A column declared `citext` is refused;
  cast the values with `::citext` instead. The PostgreSQL session functions
  (advisory locks, `txid_current`, `pg_wal_lsn_diff`, `pg_notify`,
  `pg_backend_pid`, `current_user` and others) are unknown in the SQLite
  dialect. Other stand-ins remain and agree only on the transcript, such as
  publication and replication DDL that replicates nothing; the capability
  matrix lists them all.
- `redlinedb --version` prints
  `redlinedb v5.0.0 (tested against SQLite 3.53.1)`, naming the pinned
  reference shell the corpus runs against; it no longer claims
  "SQLite 3.45.1 compatibility".

### C ABI (`libredlinedb`)

Rebuild programs compiled against the v4 headers. There is no v4
compatibility alias.

- The library is versioned: `libredlinedb.so.5` on Linux and
  `libredlinedb.5.dylib` on macOS (install name `@rpath/libredlinedb.5.dylib`),
  and `redlinedb.h` defines `RLDB_ABI_MAJOR 5`. Release archives contain only
  regular files; the installer creates the unversioned development link. A
  program linked against v4 recorded the unversioned name, which now resolves
  to v5, so rebuild it.
- `sqlite3_prepare_v3` takes upstream's argument order:
  `(db, sql, nByte, unsigned int prepFlags, ppStmt, pzTail)`. Only
  `SQLITE_PREPARE_PERSISTENT` and `SQLITE_PREPARE_NORMALIZE` are accepted;
  other flags return `SQLITE_ERROR`. `*ppStmt` is NULL on every failure, and
  the SQL is read only up to `nByte` or the first NUL.
- `SQLITE_NULL` is 5, as in upstream `sqlite3.h` (v4 defined it as 0).
  `rldb_column_type` still returns `RLDB_NULL` (0).
- Column and value text follow the storage class. `sqlite3_column_text` and
  `sqlite3_value_text` return the CAST-to-TEXT text for INTEGER and REAL
  values (v4 returned an empty string) and a NULL pointer for NULL.
  `sqlite3_column_bytes` returns the length of that text (v4 returned 8 for
  NULL and numbers), `sqlite3_column_blob` returns the converted bytes, and a
  TEXT value with an interior NUL no longer fails the step. `sqlite3_exec`
  callbacks receive the same text.
- `sqlite3_column_type` reports a REAL value as `SQLITE_FLOAT`; v4 reported it
  as INTEGER. An out-of-range column returns NULL and records `SQLITE_RANGE`.
- `sqlite3_open(":memory:")`, an empty filename and `SQLITE_OPEN_MEMORY` open
  a private in-memory database whose filename is `""`; v4 created a directory
  named `:memory:` in the working directory. Backup into such a database is
  refused. With `SQLITE_OPEN_URI`, a `file:` name is refused.
- Functions and collations registered on a connection are removed when it
  closes, and `sqlite3_create_function_v2` destructors run exactly once.
  Deleting a function returns `SQLITE_OK`; `xFunc` together with
  `xStep`/`xFinal` is `SQLITE_MISUSE`.
- Refused instead of ignored: `SQLITE_DIRECTONLY` and unknown `enc` bits,
  `sqlite3_create_window_function` with `xValue` or `xInverse`, and
  `sqlite3_trace_v2` with a callback and a non-zero mask. An authorizer
  return code other than OK, DENY or IGNORE fails the statement, and the
  authorizer receives the database name in `arg5`, as upstream.
  `sqlite3_blob_open` with `flags == 0` is read-only.
- `rldb_open_v2` checks `rldb_config`: it reads only up to `struct_size` and
  returns `RLDB_MISUSE` for a bad size, non-zero `flags`, an unknown
  `durability` or non-zero bytes past the known fields. A zero field keeps its
  default, and `durability` takes effect. `rldb_backup_init` refuses a
  non-NULL `dst_config`.
- Release builds of the library use `panic = "abort"`: an internal panic
  aborts the host process. `docs/compatibility/abi-safety.md` is the caller
  contract, and `docs/api-stability.md` says what each interface promises.

### Install and Rust dependencies

- Releases, the installer and clone URLs moved to
  `https://github.com/neverhuman/redline`. Update scripts that use the old
  repository name.
- The installer keeps each release in `PREFIX/lib/redlinedb/versions/<tag>/`;
  `PREFIX/bin`, `PREFIX/lib` and `PREFIX/include` hold links through
  `PREFIX/lib/redlinedb/current`. Scripts that read installed files directly
  may need the new paths. A prefix that an earlier installer filled is
  refused until you set `REDLINEDB_MIGRATE_LEGACY=1`, which keeps those files
  as the previous version (`REDLINEDB_ROLLBACK=1` switches back).
- The installer refuses an archive whose provenance does not name this
  repository and the requested tag, so it cannot install archives built
  before v5.0.0. It stops before writing anything on glibc older than 2.35,
  on musl and on macOS older than 15.
- The `redline-web` and `redline-testing` archives keep their licence,
  provenance and version records in `share/redlinedb/components/<package>/`.
- The crates are not published on crates.io. Depend on the tag:
  `redlinedb = { git = "https://github.com/neverhuman/redline", tag = "v5.0.0" }`.
  The Rust API may change in any release.

## Known limitations

- **SQLite.** Failing cases are listed with reasons in
  [`metadata/sqlite_parity/known-failures.json`](https://github.com/neverhuman/redline/blob/v5.0.0/metadata/sqlite_parity/known-failures.json).
  Some passing cases rely on declared stand-ins (`fts5`, `rtree`, `dbstat`
  and others), listed in the README's SQLite report. `sqlite_version()` is not
  supported. Known differences outside the corpus:
  - A failed statement inside an explicit transaction ends the whole
    transaction; SQLite rolls back only that statement.
  - The shell stops at the first error in statements read from standard
    input, with or without `-bail`; sqlite3 continues unless `-bail` is given.
  - `ORDER BY` naming a result-column alias fails with `no such column`
    unless the query has `GROUP BY`, `DISTINCT` or a window function, and
    `HAVING` cannot name an alias.
  - A window query that orders by a column not in its select list fails with
    `no such column`.
  - A `RANGE` frame with a numeric offset counts rows, not `ORDER BY`
    values, and a window frame offset that is not a literal is treated as 0.
  - `INSTEAD OF UPDATE` and `INSTEAD OF DELETE` triggers on views are not
    supported (`INSTEAD OF INSERT` is).
  - `INSERT … SELECT` fires `BEFORE INSERT` triggers but not `AFTER INSERT`
    triggers.
  - A dropped trigger's name cannot be used again (`object already exists`),
    and `CASE … END` inside a trigger body does not parse.
  - Trigger programs nest at most 8 deep; SQLite allows 1000.
  - `CREATE INDEX` does not wait for other open transactions.
  - `CREATE INDEX` on a table whose rows predate an `ALTER TABLE … ADD
    COLUMN` misses those rows (`REINDEX` repairs it), and an index on a
    `VIRTUAL` generated column finds nothing.
  - `CHECK` constraints are evaluated without comparison affinity, and the
    general `x IS y` form does not parse (`IS [NOT] DISTINCT FROM` does).
  - Views and CTEs do not carry a column's collation to their output
    columns, and a recursive CTE's columns compare with BLOB affinity rather
    than SQLite's rule.
  - Every CTE is materialized when its statement is bound, so an unused CTE
    that names a missing table is an error.
  - `REINDEX` of an attached database is not supported.
- **RQL.** 77 known RQL output divergences from SQLite are
  declared as skips, not failures, in
  [`scope-policy.json`](https://github.com/neverhuman/redline/blob/v5.0.0/subrepos/redline-testing/corpus/sqlite_parity/scope-policy.json).
- **PostgreSQL.** Only the SQL-shell corpus is measured. Wire protocol, TLS,
  roles and authorization, SQLSTATE, NOTIFY delivery, replication and
  extensions are not covered, and some passing cases agree only because a
  stand-in prints the expected transcript; see the
  [capability matrix](https://github.com/neverhuman/redline/blob/v5.0.0/docs/beyond-postgres-skips.md#capability-matrix).
  Advisory locks work only between connections of one process, and sequences
  are kept per connection. In the PostgreSQL dialect, `E'…'` strings without
  a backslash and `$$…$$` strings in plain expressions do not parse, PL/pgSQL
  substitutes variables inside string literals, and a data-modifying CTE
  (`WITH u AS (UPDATE … RETURNING *) …`) writes once, when the statement is
  prepared.
- **Durability.** Only a process crash in `Strict` mode on the tested
  filesystem is claimed. Power loss, OS crashes, `Normal` and `UnsafeDev`
  modes, and other filesystems are not. A process killed while a checkpoint
  writes its pages can leave a second copy of a recent row that a page scan
  returns twice. SQL `ATTACH` of a database directory, the C API's
  `sqlite3_open*` and `rldb_open`, the shell's `-readonly` flag and the sqlx
  `mode=ro` URL open without `owner.lock`, so point them only at a database
  no other process has open. See
  [`docs/manual/durability.md`](https://github.com/neverhuman/redline/blob/v5.0.0/docs/manual/durability.md).
- **Performance.** RedlineDB is slower than SQLite on the median per-process
  CLI case; see the table above and the README's version history. v5.0.0's
  median ratio (2.246×) is 6.3% above v4.1.0's (2.112×) on the same 1899
  cases, outside the run-to-run range. The cause has not been profiled.
- **C ABI.** An experimental subset of `sqlite3_*`; not a `libsqlite3`
  replacement. `sqlite3_libversion()` reports RedlineDB's version (`5.0.0`),
  not a SQLite version. No `SQLITE_READ` authorizer calls and no trace_v2
  events are delivered; `docs/security-capabilities.md` lists what is
  enforced.
- **Server.** `redlinedb-server` has no authentication or TLS. Bind it to
  localhost or a trusted network.
- **Deferred.** Power-loss durability evidence, a PostgreSQL wire protocol, the
  SQLite file format, crates.io publication, and wiring the optional
  `wal_pipeline` writer into the engine are not part of this release.

## Verify your download

Each archive has a `.sha256` file, build provenance that names this repository
and tag, and a GitHub build provenance attestation.

```bash
VERSION=v5.0.0
PLATFORM=linux-x86_64   # or linux-arm64, macos-x86_64, macos-arm64
ASSET=redlinedb-$VERSION-$PLATFORM.tar.gz
BASE=https://github.com/neverhuman/redline/releases/download/$VERSION
curl -fsSLO "$BASE/$ASSET"
curl -fsSLO "$BASE/$ASSET.sha256"
sha256sum -c "$ASSET.sha256"        # macOS: shasum -a 256 -c "$ASSET.sha256"
gh attestation verify "$ASSET" --repo neverhuman/redline
```

Install and smoke test (`REDLINEDB_VERIFY_ATTESTATION=1` makes the installer
run the attestation check too):

```bash
curl -fsSL https://raw.githubusercontent.com/neverhuman/redline/v5.0.0/install.sh | VERSION=v5.0.0 bash
~/.local/bin/redlinedb --version                 # prints redlinedb v5.0.0 (tested against SQLite 3.53.1)
~/.local/bin/redlinedb --build-info --json       # names the tag and commit
~/.local/bin/redlinedb -batch :memory: 'SELECT 1;'   # prints 1
```

# RedlineDB v5.0.0 launch evidence ledger

This ledger is the ID matrix for RedlineDB v5.0.0, checked against the external
launch audit of `c1af369`, the pre-launch `origin/main`. That audit rated the
tree NO-GO for an unqualified launch. The audit's workplan names every ID used
here. Each row gives the ID's final status and the commits on
`release/v5.0.0-launch` that carry it. The Acceptance column holds the command
from each commit's `Acceptance:` trailer, and most of those commit bodies also
record how the command failed on the parent. The matrix covers
`c1af369..55637d088`. Status vocabulary:

- **Done**: the workplan acceptance is met by the listed commits.
- **Rejected-at-boundary**: the feature fails closed, with a test that proves the refusal.
- **Narrowed**: the claim or scope was reduced instead of fully delivered, and the reduction is stated.
- **Deferred**: on the approved plan's explicit deferral list.

Rows marked *(plan)* are IDs that the approved execution plan or the commit
trailers added, such as NEW-01. Shard-10 gates #1–#10 map onto the rows below
through workplan §13 and are not repeated. The P1-\* trailers are Phase 1
reworks of the fix branches and appear in the [fix-branch map](#fix-branch-map).

Abbreviations used in the Acceptance column:
- `RT` = `cargo test --locked --manifest-path subrepos/redline-testing/Cargo.toml -p redline-testing`
- `RTB` = `RT --bin redline-testing`
- `BENCH` = `cargo test --locked -p redlinedb-bench`
- `KT` = `cargo test -p redlinedb-kernel --locked`
- `LWA` = `cargo nextest run -p redlinedb-sql --locked --test launch_wrong_answer_regressions`
- `FFI` = `cargo test -p redlinedb-ffi --locked`

## Decisions

- Base is `c1af369`. One PR folds the 31 fix branches, `main` is fast-forwarded to it, and the release goes out as `v5.0.0-rc.1` before `v5.0.0` on the same SHA. `v4.1.0` is never moved.
- Durability claim scope: only "Strict survives a process kill" (claim tag `durability.strict.process-kill`). OS crash and power loss are not claimed. Media corruption is detected, not repaired. Normal and tmpfs parity lanes never count as Strict evidence.
- A durability claim needs a receipt from the shipped CLI (`redlinedb-bench durability-evidence`): no failpoint build, not tmpfs or ramfs, at least 10 scenarios, and a clean tree with no binary-input change up to the release. `durability-claim-gate.sh` blocks publish without one.
- Index-format epoch 3 is the `u16` at offset 4 of every B-tree page. Opening a 4.x database rebuilds every index from the heap in one transaction. The open fails, naming the index, if the new rules make two rows share a UNIQUE key (`1`/`1.0`, NOCASE `x`/`X`, or duplicates left by partial indexes). 4.x refuses epoch-3 databases, so downgrade is refused.
- A catalog is written as format 8 once it holds any collation, and v4.1.0 refuses it. Control files are now version 2 (`heap_redo_lsn`), and older builds refuse them. This build refuses control files from newer builds (`UnsupportedVersion`).
- C ABI major 5: `libredlinedb.so.5` / `libredlinedb.5.dylib`, `RLDB_ABI_MAJOR 5`, and no v4 alias. Archives hold real files only, and the installer makes the dev link. v4 programs must be rebuilt (`prepare_v3` argument order, `SQLITE_NULL` = 5).
- Stability: `rldb_*` is stable within ABI major 5. The `sqlite3_*` subset is experimental. The Rust crates are unstable and unpublished; depend on a git tag. The C library is built with `panic = "abort"` and should be treated as fail-stop.
- Unenforced C-ABI features fail closed instead of returning OK: `SQLITE_DIRECTONLY`, unknown `enc` bits, `trace_v2` callbacks, and window `xValue`/`xInverse`. `docs/security-capabilities.md` lists them.
- PostgreSQL is claimed only as the PostgreSQL 16.15 SQL-shell corpus. Wire protocol, TLS, roles, SQLSTATE, NOTIFY delivery, replication and extensions are unverified or unsupported.
- Declared unsupported in PG mode (`UnsupportedCapability`): `pg_current_wal_lsn`, `pg_export_snapshot`, `pg_notify`, `NOTIFY`, `citext` columns, and `pg_listening_channels()` outside a bare SELECT list. The 11 corpus cases that call these are `declared_unsupported`. In the SQLite dialect, `pg_*` functions do not exist.
- The SQL dialect is fixed per database (`DbOptions::dialect`). `REDLINEDB_RESULT_DIALECT` is read once, at open.
- SQLite corpus: the oracle is the pinned 3.53.1 build. Failures are published through the `known-failures.json` ratchet and never relaxed. A case may be skipped only if `scope-policy.json` lists it. Declared deviations are 00093–00096 (fts5/rtree/dbstat stand-ins), 10405 and 12023.
- Performance numbers are raw per-case ratios with no floor. The README SQLite block reports correctness only. The version table renders only from a publishable release-bench bundle (K ≥ 3, `--workers 1`, pinned CPUs). No speedup is claimed or required.
- Savepoint statements act when stepped. `ROLLBACK TO` replays in the transaction's own snapshot and refuses replay-unsafe prefixes. Exact undo is deferred.
- Unused-CTE eager materialization is a declared deviation. Parameters in `CREATE VIEW` are refused, as in SQLite. Trigger nesting is capped at 8 (SQLite: 1000).
- `owner.lock` is exclusive, including for read-only opens, and is held until the last connection drops. The shell's `-readonly`, sqlx `mode=ro`, SQL `ATTACH` and the C API opens do not take it (manual chapter 09).
- Pressure checkpoints are on for persistent SQL databases. Backups hold off checkpoints until their copy is done.
- The only release authority is `neverhuman/redline` (repository id 1390165945, `ops/release/authority.env`). The installer refuses archives whose provenance lacks that id, which includes every older archive.
- The installer installs into `versions/<tag>` and activates it with an atomic `current` link. It refuses glibc < 2.35 and macOS < 15, never overwrites files it did not create, and migrates legacy flat installs only when asked.
- Fork PRs run only on hosted runners, and `RedlineDB/required` reports "Maintainer run required" until a maintainer runs CI. `main` takes rebases only, behind strict `RedlineDB/required`, one review, linear history and `enforce_admins`.
- `SECURITY.md` points only at GitHub private vulnerability reporting; there is no mailbox. 5.0.x is supported and 4.x is unsupported from 5.0.0.
- Release tags are `vX.Y.Z` / `vX.Y.Z-rc.N`, admitted by `ops/ci/release-version.sh check`. The parity report bot runs only on dispatch.

## Known defects at release

Each item below is still open according to the lane notes.

Durability and storage:
- **Duplicate row after a crash mid-checkpoint.** If a process dies during a checkpoint's page writes, before its control slot lands, a heap row can end up stored twice. Row-id reads return one version, but a page scan can return the row twice. Tracked in `docs/manual/durability.md`; the recover oracle rejects duplicates (479778b55).
- **Opens that skip the owner lock.** The shell's `-readonly`, sqlx `mode=ro`, SQL `ATTACH` of a directory and C API opens (`sqlite3_open*`, `rldb_open`) run recovery without `owner.lock`. Tracked in `docs/manual/09-operate.md`.
- **Directory fsync gaps.** Removing a WAL segment after a checkpoint does not fsync the directory, so a removed segment can reappear after a crash; recovery of that case is untested. The multi-lane WAL and `wal_pipeline` also skip directory fsync, but neither is used by default. Limits are in `docs/manual/durability.md`.
- **Files from before v5.** A delete and reinsert of one row inside one transaction, written before v5, is not linked, so a directory rebuild picks the version by page position. Pages past a v1 (v4.1.0) checkpoint's page count keep v4.1.0's duplicate-row risk until this build's first checkpoint.
- **Visibility wait.** Schema and index handles publish with the transaction, not the CSN frontier. A statement that starts during COMMIT's visibility wait can see a new table before its rows.
- **Downgrade after a targeted restore.** Binaries older than v5 ignore the `TimelineFork` record, so they replay past a targeted restore's cut.
- **Non-Unix platforms.** The Windows `LockFileEx` owner lock is untested, and directory fsync is a no-op off Unix.

SQL:
- **Index on a table altered with ADD COLUMN.** `CREATE INDEX` over rows stored before `ALTER TABLE … ADD COLUMN` reads their keys from the wrong column. `integrity_check` reports it and `REINDEX` repairs it.
- **Index on a VIRTUAL generated column.** Such an index gets NULL keys, so lookups through it find nothing.
- **RANGE frames with a numeric offset** span that many rows instead of the ORDER BY values within the offset.
- **CHECK constraints** run without comparison affinity, and the general `x IS y` form does not parse.
- **Aliases.** `ORDER BY <alias>` without GROUP BY, DISTINCT or a window fails with `no such column`, and HAVING cannot name an alias.
- **Collations through views.** Views and CTEs do not carry a column's collation to their output columns.
- **REINDEX and CREATE INDEX.** REINDEX of an attached database is unsupported. A custom collation is recognized only when an index uses it. CREATE INDEX does not wait for other transactions.
- **Data-modifying CTE (PG dialect).** It writes at prepare, so a reset and re-step does not write again.
- **Triggers.** `INSTEAD OF UPDATE`/`DELETE` are unsupported. `CASE … END` in a trigger body fails to parse. Re-creating a dropped trigger's name fails with "object already exists".
- **SQLite corpus failures.** The cases listed in `metadata/sqlite_parity/known-failures.json` still fail (77 `sqlite_parity` + 77 `memory` entries as committed). They include error-message shapes, EXPLAIN bytecode, `.bail`/`.crlf`, 10413, 10570 and BLOB hex output. The ratchet enforces the list, and the affected rows in `docs/sqlite-feature-matrix.json` are partial.

C ABI, packaging and CI:
- **C ABI gaps.** There are no `SQLITE_READ` authorizer calls and no `trace_v2` events, and the trace/profile/commit hooks fire only from `sqlite3_exec`. Tracked in `docs/security-capabilities.md`.
- **macOS install path untested locally.** The installer's `mv -h` activation and `@rpath` lookup through the stable links run only on the hosted macOS runners.
- **SQ-08 scope.** There is no stateful prepared-statement qualification lane. The Rust-values lane uses rusqlite's bundled SQLite 3.50.2, not 3.53.1.
- **Legacy chaos-suite name.** The old name survives in `CHANGELOG.md` history, `.jankurai/repo-score.json`, `jankurai-score.txt` and the hashed audit baselines. These are exempted in `scripts/check-public-hygiene.sh`.
